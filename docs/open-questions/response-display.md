## 背景

Phase 3 で指示(instruction)を送れるようになったが、エージェントの
応答テキストはどこにも表示されない(ダッシュボードにも wrapper の
ターミナルにも出ない。2026-06-11 の実運用検証初日に顕在化)。
プロトコルの type には `log` / `result` が予約済み
([ADR-0010](../adr/0010-protocol-precisification.md))で中継の設計
予定地はあるが、**表示 UI の方向性はユーザが慎重に決めたい意向**。

[non-goals](../specs/non-goals.md) は同梱ダッシュボードを「状態一覧・
表情・承認・指示入力」の最小限に限定しており(リッチな UX は外部
クライアントの領分、[ADR-0007](../adr/0007-client-separation-reference-dashboard.md))、
返答表示はこのリストに**含まれていない**。スコープ線引きの再判断が
本質的な論点。

## 選択肢

| 案 | 内容 | メリット | デメリット |
|----|------|----------|-----------|
| A | result 中継のみ: ターン完了時の最終応答を `result` type で中継し、カードに最新 1 件を折りたたみ表示 | 実装小。「指示の結果が見える」最小限で状態可視化の主目的を保つ | ターン途中の経過は見えない |
| B | ログストリーム: assistant テキストを `log` type で逐次中継、カードに直近 N 件表示 | 経過が見える | wire 量増。チャット UI に接近し non-goals の線引きが曖昧化 |
| C | プロトコル中継のみ実装し、表示は外部クライアントへ委譲 | non-goals に忠実 | 同梱ダッシュボードだけでは検証が完結しない |
| D | カードからの会話ペイン(フルチャット) | 完全な対話体験 | non-goals(同梱クライアントのリッチ化)に正面から抵触 |

## 影響

未決の間、ダッシュボードからの指示は「届いたが何と答えたか見えない」
状態で、双方向機能の実用性が大きく限定される(実運用検証のブロッカー)。

## 判断材料

- kaoiro の目的は状態可視化([overview](../specs/overview.md))。
  「指示の結果確認」をどこまで同梱ダッシュボードの責務に含めるか。
- 応答テキストにはシークレットが混入し得る
  ([threat-model](../specs/threat-model.md) の tool input と同型の問題)。
  viewer への配信制御・サイズ上限の要否。
- エンベロープ 64KB 上限([protocol](../specs/protocol.md))との関係
  (長文応答の切り詰め方)。
- 中継(プロトコル)と表示(UI)は分離して決められる: 中継仕様は
  どの案でもほぼ共通で、UI の選択が本質。
