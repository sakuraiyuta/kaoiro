# Claude SDK-created notification turn lifecycle

## Decision and evidence

Implement option A in two commits: first correct the local `unbound_tool_call` and `stale_tool_call` guidance from [the frozen option-B proposal](https://github.com/sakuraiyuta/kaoiro/blob/f7035c18a909bcdca5376387d7942cd57dc6fc0a/docs/plans/issue-422-notification-origin.md), then admit a **new, independently owned SDK notification turn**. A completed task does not extend its launching token. An MCP handler never borrows the current token or latest snapshot. The operator selected A; the first commit gives an honest error while the lifecycle is introduced.

The [original actual-host reproduction](https://github.com/sakuraiyuta/kaoiro/blob/f7035c18a909bcdca5376387d7942cd57dc6fc0a/docs/evidence/2026-09-27-issue-422-notification-turn.md) establishes the failure and the late `result.origin.kind=task-notification`. [Our hook measurement](../evidence/2026-09-27-issue-422-prompt-boundary.md) adds a usable pre-tool boundary: in three actual SDK 0.3.280 / CLI 2.1.280 queries, a notification continuation fired `UserPromptSubmit` with a new `prompt_id` before its model/tool activity; `PreToolUse` for `send_to_agent` carried the same ID and preceded the MCP callback. Its hook prompt contained a `<task-notification>` document whose fields matched the earlier SDK `system/task_notification`. `source` was absent in **both** wrapper and notification prompts in the two runs that recorded that field. This is one background-Bash path; the race and failure paths below remain implementation gates. The three added queries caused 15 recorded model API dispatches. No model API is needed in ordinary automated tests.

## Admission invariant

Each accepted tool call ID must map to exactly one live token belonging to the SDK prompt that produced it. A prompt admitted from a task notification gets its own token and an immutable basis copied from peer input previously handed to this session. A queue entry, task completion frame, `system/init`, assistant frame, or `result.origin` alone grants no origin. An unknown, ambiguous, duplicated, subagent, retired, or wrong-session ID is rejected locally with zero sends. Server-side `in_reply_to` comparison and ticket checks remain intact.

The notification snapshot is intentionally conservative. Add per-token confirmed-delivery records and a session-level completed ledger to `InterAgentTool`/`ReplyBasis`. Record a wrapper input only when its SDK prompt is correlated; record a recovery or waiter envelope only after the actual result handoff commits. At **every** wrapper or notification token's terminal boundary, merge that token's confirmed inputs into the completed ledger before retiring the token, including inputs already handed off before an abort or API error. An uncommitted handoff and a queued input never enter it. A notification's snapshot is a fixed copy of the completed ledger at its `UserPromptSubmit` callback; later handoffs change only the next token's snapshot. Thus a concurrent wrapper input may be omitted, but cannot be borrowed. A genuinely newer, still queued peer turn can produce the server's normal stale-basis recovery; a turn already handed off is no longer in that queue, so the ledger must retain it. No old reply ticket crosses tokens; a notification turn can use only tickets issued by a tool result within that new turn.

## Correlation and lifecycle

1. On an SDK `system/task_notification`, retain a bounded, one-use candidate `(session_id, task_id, tool_use_id, status, output_file, summary)`; require that the task belongs to the root host's observed task ledger. This frame **does not** begin a turn. Drop candidates on session change, interrupt, host close, reset, or expiry. Multiple completions may be coalesced into one hook prompt; match every embedded notification to a candidate and consume the set atomically.
2. Register host-owned `UserPromptSubmit`, `PreToolUse`, and `Stop` hooks **after** user hooks so query options cannot replace them. For an SDK prompt, use `source` when present, but never require it: it is absent in measured 0.3.280. Without `source`, match the hook's exact parsed `<task-notification>` fields to the candidate set. A new root prompt ID (`agent_id` absent) with a unique match starts the notification token before the hook returns. A wrapper prompt is correlated to its single outstanding yielded input by its text/content representation; if it and a notification could both match, or the content cannot be correlated, deny origin rather than guess. A nonmatching synthetic/system prompt grants no reply origin. A repeated prompt ID, missing ID, mismatched session, malformed notification, or unexpected task is unbound. Retain only bounded prompt and call-ID maps; do not log prompt bodies.
3. `PreToolUse` checks `agent_id` is absent, finds the live `(session_id, prompt_id)` owner, and binds `tool_use_id` **before** tool execution. The MCP resolver waits only for that explicit binding; it no longer uses the global current-turn fallback for inter-agent calls. The existing `canUseTool` permission path remains a second guard where it runs, but the hook and shared-tool guard are required because `bypassPermissions` shadows `canUseTool` in the measured run. Duplicate call IDs with different owners are permanently denied. `Stop` is only a stop **attempt**: [hook decision control](https://code.claude.com/docs/en/hooks#stop-decision-control) may add context and the same prompt may call another tool before a second Stop. Keep its token, permission ownership, and watchdog live until its matching terminal result or explicit cancellation. Interrupt/EOF/watchdog/reset retire it immediately; late callbacks remain stale.
4. Treat the notification as an actual host turn with `kind: sdk_notification`, its own initially empty coordinator-CID list, reply snapshot, permission-wait ownership, state/progress, and watchdog token. The CLI starts/ends `InterAgentTool` and watchdog for that token. It does **not** settle `InterAgentTurnCoordinator`, acknowledge queued deliveries, or resolve any other wrapper token. A committed recovery handoff may call `notePendingInjection(envelope, notificationToken)`; derive the CIDs still owned by that exact notification token from the pending-injection map, not from a separate historical CID list. At its terminal result, call `resolveTurnEnd(notificationToken, ownedCids, classifiedError)` for those CIDs only, then retire the reply token. Successful outbound replies already clear their pending entries; success clears any remaining entries without a notice; error/interrupt emits a turn-failure notice for each still-unanswered entry. A rolled-back handoff transfers neither basis nor reply obligation. `sessionReset.onTurnEnd` runs after a real notification terminal result only. The existing wrapper-input kind keeps its coordinator behavior.
5. Extend the host input barrier to hold the next queued wrapper input while a notification candidate is being admitted or an admitted notification turn is active. A candidate without a matching prompt is released after a bounded admission deadline; a hook arriving after release cannot retroactively claim a token. If a wrapper input was already yielded when a notification is observed, keep that wrapper token, reject an ambiguous notification prompt, and attribute each terminal result by its owner. Specifically, `result.origin.kind=task-notification` must never retire a wrapper-input token or release its queue barrier. If terminal ownership cannot be established, fail-stop admission rather than settle the wrong token. Do not use a longer model/tool timeout as the fix.
6. The current `TurnWatchdog` owns one token. The queue barrier preserves that invariant for the accepted path. A racing SDK prompt that cannot be serialized is unbound, with a diagnostic; it must not start a second watchdog or borrow the first one's progress. SDK frames associated with the admitted notification count as progress; its exact result ends the watch. Permission dialogs use the notification token and are withdrawn on its abort/result. A session change clears candidates, prompt bindings, origin records, basis snapshots, and watches before new input is admitted.

The host uses these bounded states for a notification prompt:

| State and event | Owner, watchdog, and permission waits | Queue and retirement |
| --- | --- | --- |
| Candidate after `task_notification` | No reply token, watch, or permission owner. | Hold the next input only until hook admission or the fixed admission deadline. |
| Admitted `UserPromptSubmit` | New prompt-ID token and immutable basis; one watchdog. | Hold the next wrapper input until this token's terminal result. |
| `Stop` attempt, then continued `PreToolUse`, another `Stop`, or `StopFailure` | **Same** token and watch; new calls still bind to its prompt ID. `StopFailure` is diagnostic, not retirement. | Keep the barrier closed; do not clear permission ownership or tickets. |
| Matching result, success or error | Resolve only this token's committed recovery CIDs; merge confirmed handoffs; withdraw remaining permission waits; end watch and retire calls/tickets. | Open the next-input barrier after the result is attributed. |
| Interrupt, EOF, reset, or watchdog fail-stop | Abort the exact token; settle its committed recovery obligations with the classified error; clear all waits and watches. | Release or close admission according to the host's existing terminal policy; never assign a late call to the next token. |
| Candidate expired, rejected prompt, or notification result while a wrapper input is active | No new notification origin or watch; its calls remain unbound. | Preserve the wrapper owner and queue barrier. A late notification result cannot close that wrapper turn. |

A missing `Stop`, missing `result.origin`, or differing SDK ordering is handled conservatively and covered by negative tests. The measured happy path is not generalized to all CLI versions without those tests.

## Alternatives and scope

| Choice | Decision |
| --- | --- |
| Keep the launching token alive | Rejected: it would reuse authorization after the launching result retired it. |
| Bind an unknown MCP call to the latest snapshot | Rejected: queued or unrelated input could become its reply basis. |
| Detect a new turn at `task_notification` or `system/init` | Rejected: neither proves that notification text entered a model request. |
| Use only `result.origin` | Rejected for admission: it arrives after the tool call; use it only to route terminal results. |
| Use `UserPromptSubmit` plus prompt-ID tool binding | Adopted, conditional on the actual-CLI race gates below. The hook is the observed pre-model boundary. |

Product scope: `wrapper/claude-code` host, CLI lifecycle and its focused tests; `wrapper/agent-common` origin/basis and guidance; Claude event, reply-basis and errors references. No server/protocol/schema changes, no Codex or Antigravity behavior change, no automatic retry of a rejected send, and no change to issue 419's resume/schema question. SDK-internal notification markup is version-sensitive; unknown shapes fail closed and appear in a bounded diagnostic.

## Verification before implementation review

- **Actual SDK gate:** repeat the real-host notification reproduction after the change with a recorder: background Bash `WAITING` result retires T1; notification hook admits T2; B without ticket sends once with the previously completed peer basis; the target sees one send; T1's old call remains rejected. **Also require a real background Agent completion and a successful root `send_to_agent` from its notification continuation.** Exercise a child-agent tool callback as a negative control: it must not borrow the root token or send. Compare root/child hook IDs and result ownership even if their notification markup looks identical. Record SDK/CLI versions, process exits, model API dispatch count, prompt-ID/hook/result order, and source artifact hashes. Combine the Agent run with other race/cancel probes where possible to minimize actual model calls.
- **Queue race:** controlled SDK iterator plus an actual-CLI run with a next host input queued before task completion. Exercise notification first, wrapper input first, multiple/coalesced notifications, candidate expiry, and a notification during an active turn. Assert each call's token/basis, no queued peer basis in the notification snapshot, no premature `resolveTurnEnd`, exactly one watchdog owner, and no wrong-result settlement. If an actual-CLI race cannot be exercised reliably, do not claim it closed from a fake iterator alone; report the remaining boundary before enabling notification admission.
- **Confirmed-delivery sequence:** hand off peer turn 3 in notification N, then end N. N2's default basis must be 3, N's old ticket must be invalid, and queued but undelivered turn 5 must be absent. Repeat with N ending in API error after turn 3 was handed off: turn 3 remains in the later ledger. A handoff that fails before its write boundary must not advance the ledger. Mutation: suppress the notification-token merge; N2 must become stale in the fixture's real server comparison.
- **Recovery ownership:** after a committed recovery handoff in N, assert that a successful reply clears its obligation; a successful N with no reply clears only N's pending obligation; an error/interrupt emits one failure notice for each still-unanswered N-owned CID; rollback creates none. Assert an unrelated wrapper token's coordinator and pending CID remain untouched. Mutation: omit N's `resolveTurnEnd`; the error-path notice assertion must fail.
- **Negative controls:** remove the `UserPromptSubmit` admission, the `PreToolUse` prompt-ID check, the candidate match, and the terminal-origin route one at a time; the corresponding send/no-send or queue test must go red, then green on byte restoration. Absent `prompt_id`, `source` omitted, wrong/missing candidate, forged notification text, subagent ID, reused call ID, old session, expired candidate, stale token, failed handoff, late callback, and missing result must each produce zero unintended sends. Preserve exact message counts at the recorder/server seam.
- **Lifecycle gates:** interrupt, watchdog fail-stop, EOF, reset/resume, permission ask/cancel, and notification with no continuation release every queue/permission wait in bounded time. Include `Stop → continued tool → Stop → result`, `StopFailure` or no Stop, and a rejected notification prompt whose result arrives while a wrapper input waits. Assert exact owner, progress, retirement, and queue release against the state table. A notification result must not settle a wrapper turn. Existing no-injection default host test must pass through the first meaningful turn. Keep attachment input coverage when correlating ordinary wrapper prompts.
- Run `pnpm build`, `pnpm typecheck`, and full `pnpm test` in affected wrapper packages; run runner typecheck/test because wrapper source affects runtime-asset checks; record all exit codes and unhandled errors. Review the final diff, not just the initial hook implementation. Update `docs/reference/engines/claude-events.md`, `docs/reference/inter-agent/reply-basis.md`, and `docs/reference/inter-agent/errors.md`, with new implementation evidence bound to the final commit.

**Implementation gate:** if the actual SDK does not provide a unique hook-to-tool-to-result attribution under queued-input competition, stop before admitting the notification path and return that evidence for a direction decision. Accurate guidance from the first stage can stand alone while A remains unresolved.
