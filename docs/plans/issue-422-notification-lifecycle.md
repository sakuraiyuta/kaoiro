# Claude notification continuation ownership

## Decision and evidence

Implement option A with two notification shapes: **a notification folded into an already confirmed, live root wrapper turn**, and **an independently started notification turn** after the earlier turn ended. A completed task does not extend its launching token. An MCP handler never borrows the latest token or snapshot merely because it is current. The diagnostic-only option B is separate on branch `issue-422-guidance`; its landing does not enable option A.

The [original actual-host reproduction](https://github.com/sakuraiyuta/kaoiro/blob/f7035c18a909bcdca5376387d7942cd57dc6fc0a/docs/evidence/2026-09-27-issue-422-notification-turn.md) establishes the failure and the late `result.origin.kind=task-notification`. [The first hook measurement](../evidence/2026-09-27-issue-422-prompt-boundary.md) established a new `prompt_id` for a notification after a finished background-Bash turn. [The implementation gate](../evidence/2026-09-27-issue-422-implementation-gate.md) then measured a different SDK 0.3.280 / CLI 2.1.280 order: a background Bash notification arrived while T2's foreground Bash call was active; the notification `UserPromptSubmit` and its later root `PreToolUse` reused T2's `prompt_id`, and one ordinary T2 result ended both. This is a fold into T2, not an independent SDK turn. The recorder saw a send with T2's token, but T2's synthetic peer fixture reused turn 1, so that experiment does not prove the correctness of a distinct T2 peer basis. The Agent notification also used a different markup shape from Bash. The later targeted Agent observation is described below.

## Admission invariant

Each accepted root tool call ID must map to exactly one live token belonging to the SDK turn that generated it. A notification folded into an existing confirmed root prompt stays with that prompt's token and fixed snapshot; it does not create a new token, snapshot, watchdog, or delivery acknowledgement. Only a notification with a unique new root prompt ID and **no live owner** gets its own token and a fixed copy of completed peer input. A queue entry, task frame, `system/init`, assistant frame, matching prompt-ID string alone, or `result.origin` alone grants no origin. An unknown, ambiguous, duplicated, subagent, retired, wrong-session, or unconfirmed-input ID is rejected locally with zero sends. Server-side `in_reply_to` comparison and ticket checks remain intact.

The independent notification snapshot is intentionally conservative. Add per-token confirmed-delivery records and a session-level completed ledger to `InterAgentTool`/`ReplyBasis`. Record a wrapper input only when its SDK prompt is correlated; record a recovery or waiter envelope only after its actual result handoff commits. At **every** wrapper or independent-notification token's terminal boundary, merge that token's confirmed inputs into the completed ledger before retiring it, including handoffs already committed before abort or API error. An uncommitted handoff and a queued input never enter it. An independent notification takes a fixed copy of the completed ledger at its `UserPromptSubmit`; a fold keeps its live wrapper owner's earlier immutable snapshot, with no new peer basis supplied by the notification itself. Later handoffs affect only later tokens. No reply ticket crosses tokens; folded calls use only tickets issued to the existing T2 token, and independent calls use only tickets issued within their new token.

## Correlation and lifecycle

1. On an SDK `system/task_notification`, retain a bounded, one-use candidate tied to the root host's prior `task_started` record, session/generation, task ID, tool-use ID, task type and status. Bash matching requires the exact `output_file` and summary in the hook. Agent matching has two known hook forms: when `<output-file>` is strictly absent, require the known background task's one-use candidate, matching session/generation, task ID, parent tool-use ID and status, and the SDK summary exactly in `<result>`; when `<output-file>` is present, require all those conditions **and** byte-for-byte equality with the concrete SDK frame `output_file`. Do not normalize paths or compare basenames. The parser must preserve field presence and cardinality: a present but empty, duplicated, or malformed `<output-file>` is invalid, never the absent form. Reject unknown tasks, absent/expired/consumed candidates, wrong session or parent tool-use ID, and unknown markup. This frame **does not** begin a turn. Drop candidates on session change, interrupt, host close, reset, or expiry; consume a matched set atomically when several notifications share one hook prompt.
2. Register host-owned `UserPromptSubmit`, `PreToolUse`, and `Stop` hooks **after** user hooks so query options cannot replace them. `source` is optional in measured SDK 0.3.280. A wrapper prompt is correlated to exactly one yielded wrapper input by its actual text/content representation and becomes a confirmed, live `(session/generation, prompt_id, token)` root owner. When a later notification hook matches real task candidates and carries **that same prompt ID**, admit a fold only if this owner is still live, its input was confirmed, and its session/generation and root identity match. Consume the candidates, preserve its token/snapshot/watch, and record that the notification joined this owner. When there is no live owner and the notification hook has a fresh root prompt ID with a unique candidate match, start a new independent token. A reused retired ID is never fresh. If a live owner exists under a different prompt ID, or both wrapper and notification matching are possible, deny the new prompt's origin instead of binding it to the latest owner. A notification-shaped hook sharing a live ID but failing candidate validation taints that ID for **future** inter-agent call bindings; previously bound calls retain their original owner. A repeated notification hook with an already consumed candidate cannot re-admit it.
3. `PreToolUse` checks `agent_id` is absent, finds the live and confirmed `(session/generation, prompt_id)` owner, and binds a **new** `tool_use_id` before tool execution. A folded prompt may use the same owner's ID only after its candidate was matched; a subagent or an unrelated/reused ID cannot. The MCP resolver waits only for that explicit call binding, never for the current-token fallback. Retired call IDs stay retired even if T2 later starts with a different snapshot. The existing `canUseTool` permission path remains a second guard where it runs, but the hook and shared-tool guard are required because `bypassPermissions` shadows `canUseTool` in the measured run. Duplicate call IDs with different owners are permanently denied. `Stop` is only a stop **attempt**: [hook decision control](https://code.claude.com/docs/en/hooks#stop-decision-control) may add context and the same prompt may call another tool before a second Stop. The token, permission waits, and watchdog survive until its actual terminal result or cancellation.
4. An independent notification has `kind: sdk_notification`, its own initially empty coordinator-CID list, reply snapshot, permission-wait ownership, state/progress, and watchdog token. It does **not** settle `InterAgentTurnCoordinator` or acknowledge queued deliveries. A fold retains the wrapper owner's kind and all existing coordinator/watch state; it adds **no** independent terminal callback, delivery acknowledgement, or reset transition. Its one ordinary T2 result/abort settles T2 exactly once. `result.origin.kind=task-notification` may close only an independently admitted notification. An unowned or mismatched result must not close a wrapper turn.
5. On any token, a committed recovery handoff may call `notePendingInjection(envelope, token)`. At terminal, derive the exact CIDs still owned by that token from the pending-injection map. For a wrapper turn, union those CIDs with its existing coordinator batch CIDs and call `resolveTurnEnd` **once per CID before dispatching a same-peer successor**; for an independent notification use only its own recovered CIDs. Do not settle another token's coordinator or pending CIDs. Successful outbound sends already clear their pending records; success clears any remaining owned records without notice, while error/interrupt emits one failure notice per unanswered CID. A rolled-back handoff transfers neither basis nor obligation. Merge this token's confirmed handoffs to the completed ledger before retiring its calls and tickets. `sessionReset.onTurnEnd` runs only at the real terminal result, once for a fold.
6. Hold the next queued wrapper input while an unmatched candidate might start an independent notification or while an independent notification is active. A candidate without a matching hook expires after a bounded deadline; it cannot claim a token after release. A notification folded into T2 keeps T2's existing input barrier and watchdog; it does not delay T2 merely because its task candidate was observed. The same-ID fold is allowed only by the full owner-and-candidate rule above; a different-ID race fails closed. Interrupt/EOF/watchdog/reset retire the exact owner and all its bindings. A session change clears candidates, prompt bindings, origin records, basis snapshots, and watches before new input is admitted. Do not extend model/tool timeouts to make this work.

The host uses these bounded states for a notification prompt:

| State and event | Owner, watchdog, and permission waits | Queue and retirement |
| --- | --- | --- |
| Candidate after `task_notification` | No new reply token, watch, or permission owner. | Hold the next input only if no root turn currently owns the input barrier. |
| Same-ID fold into confirmed T2 | T2 remains the sole owner with its fixed basis, watch, and permission waits. | Consume the matched candidate; T2 keeps its ordinary queue barrier and one terminal result. |
| New-ID independent admission without a live owner | New token and completed-ledger snapshot; one watchdog. | Hold the next wrapper input until its own terminal result. |
| `Stop` attempt, then continued `PreToolUse`, another `Stop`, or `StopFailure` | Keep the same owner and watch; `StopFailure` is diagnostic. | Keep the existing barrier closed; do not clear permissions or tickets. |
| Matching result, success or error | Resolve only this token's coordinator and committed recovery CIDs; merge confirmed handoffs; withdraw waits; end its watch and retire calls/tickets. | Open its barrier after result attribution; a fold has no second terminal. |
| Interrupt, EOF, reset, or watchdog fail-stop | Abort the exact token; settle its committed recovery obligations with the classified error; clear waits and watches. | Release or close admission according to existing terminal policy; a late call never moves to a newer token. |
| Candidate expired, bad candidate on a live prompt, different-ID collision, or mismatched result | No new notification origin. A bad candidate sharing a live ID blocks future IA bindings under that ID. | Preserve the existing wrapper owner; no notification callback may settle it. |

A missing `Stop` is harmless. A missing `result.origin` is expected for the measured fold and may terminate its confirmed wrapper owner once; it is not sufficient to terminate an independent notification. Differing SDK ordering is handled conservatively and covered by negative tests.

## Alternatives and scope

| Choice | Decision |
| --- | --- |
| Keep the launching token alive | Rejected: it would reuse authorization after the launching result retired it. |
| Bind an unknown MCP call to the latest snapshot | Rejected: queued or unrelated input could become its reply basis. |
| Detect a new turn at `task_notification` or `system/init` | Rejected: neither proves that notification text entered a model request. |
| Use only `result.origin` | Rejected for admission: it arrives after the tool call; use it only to route terminal results. |
| Always create a new notification token | Rejected by [the measured fold](../evidence/2026-09-27-issue-422-implementation-gate.md): the SDK can reuse a live wrapper prompt ID and emit only its ordinary result. |
| Treat every same-ID hook as a fold | Rejected: a string match without a confirmed live root input, matching task candidate, and matching session/generation could authorize an unrelated call. |
| Classify a validated same-owner fold or a fresh independent prompt | Adopted, conditional on the actual-CLI gates below. The hook is the observed pre-tool boundary; the fixed owner and actual input decide its reply basis. |

Product scope: `wrapper/claude-code` host, CLI lifecycle and focused tests; `wrapper/agent-common` origin/basis and notification recovery ownership; Claude event and reply-basis references. B's guidance and errors reference are on the separate `issue-422-guidance` branch. No server/protocol/schema changes, no Codex or Antigravity behavior change, no automatic retry of a rejected send, and no change to issue 419's resume/schema question. SDK-internal notification markup is version-sensitive; unknown shapes fail closed and appear in a bounded diagnostic.

## Verification before implementation review

- **Actual SDK gate for both shapes:** repeat an independent background Bash completion after T1 ends; its root call gets a new notification token and the completed-ledger basis. A real background Agent must likewise produce a successful root send, while a child-agent callback produces zero sends. Pin both observed Agent frame-to-hook forms (strictly absent `<output-file>` and present exact path), plus empty, duplicate, malformed, and mismatched paths as rejection controls. A path-equality-guard mutation must turn the present-path test red; restore it byte-for-byte and rerun green. Missing, expired, or consumed candidates and wrong session/parent tool-use ID must also reject. Re-measure root success and child rejection through the final built `runClaudeCli` composition after the matcher changes. Record SDK/CLI versions, process exits, model API dispatch count, hook/call/result order, and source/artifact hashes. The prior unqueued Bash and Agent probes support feasibility but cannot validate the revised implementation.
- **Distinct-input fold gate:** in an actual SDK/CLI run, hand peer turn 1 with body A to T1, then peer turn 3 with **different body B** to T2 as actual SDK input. Complete T1's background task while T2 is live; its notification hook and a newly generated root call must correlate to confirmed T2 and retain fixed default `in_reply_to=3`. Separate the server comparisons by the latest **server-accepted** peer turn in that CID: **(a)** while the server's latest is 3, a folded call with default basis 3 makes one wrapper send attempt, one server acceptance and one peer delivery. A deliberately stale basis 1 sent through the real joined server channel as a comparison control makes one server push attempt, one `stale_reply_basis` rejection and zero peer deliveries; it is counted separately from wrapper tool attempts because the v1 ticket guard does not permit fabricating that explicit basis in T2. **(b)** then have the real server accept ordinary peer turn 5 and deliver it to the host, but keep it queued without yielding it to the SDK. A subsequent folded T2 call still defaults to basis 3; its one wrapper attempt must be rejected by the server as `stale_reply_basis(expected_peer_turn=5, supplied_basis=3)` with zero peer deliveries. If recovery later hands off body 5, count any ticket-authorized intentional resend separately; the unchanged T2 default must remain 3. These observations may share one actual-CLI run if the test controls ordering, but must use actual SDK inputs and the real join/send comparison rather than changing fixture bookkeeping or server rules. **(c)** hold a root call captured under T1 before its interrupt/result, then release it during T2: it must make zero wrapper-to-server send attempts even though T2 is live. The T1 held-call experiment may use the SDK MCP callback barrier from the issue-407 origin gate; record whether it was actually captured before retirement. If the native CLI cannot produce one of these boundaries, report that gap rather than inferring it from a mock.
- **Queue and ownership controls:** in controlled SDK iterators plus the actual-CLI fold run, cover notification first, wrapper input first, coalesced task candidates, candidate expiry, and a different-ID prompt while a wrapper owner is live. Assert exact root prompt ID, generation, task candidate, token, basis, one watchdog, one terminal result, and no premature coordinator settlement. Mutate the candidate match and owner-confirmation checks separately; each matching test must turn red, then green after byte restoration. A notification-shaped hook sharing T2's ID but lacking a valid candidate must taint later IA bindings without invalidating an already captured T2 call. A root tool call under a different ID must remain unbound.
- **Confirmed-delivery sequence:** hand off peer turn 3 in notification N, then end N. N2's default basis must be 3, N's old ticket must be invalid, and queued but undelivered turn 5 must be absent. Repeat with N ending in API error after turn 3 was handed off: turn 3 remains in the later ledger. A handoff that fails before its write boundary must not advance the ledger. For the ledger-merge mutation, hold the server's latest accepted peer turn at **3**: unmutated N2 defaults to 3 and the real server accepts/delivers its send; suppressing only the N→completed-ledger merge makes N2 use the older basis and the same server comparison rejects it. The separate stage after server acceptance of turn 5 must reject default basis 3 in both builds and cannot serve as this mutation's proof.
- **Recovery ownership:** after a committed recovery handoff in independent N or folded T2, assert that a successful reply clears its obligation; a successful turn with no reply clears only its own pending obligations; an error/interrupt emits one failure notice for each still-unanswered owned CID; rollback creates none. The wrapper coordinator's batch CIDs and newly recovered CIDs are resolved once each before a same-peer successor dispatches, without touching another token. Mutate the union of recovered CIDs into T2 settlement and N settlement independently; each failure-notice assertion must turn red.
- **Negative controls:** remove independent `UserPromptSubmit` admission, same-owner fold classification, `PreToolUse` prompt-ID check, candidate matching, old-call retirement, and terminal routing one at a time; the corresponding send/no-send or queue test must go red, then green on byte restoration. Absent `prompt_id`, `source` omitted, wrong/missing candidate, forged notification text, subagent ID, reused call ID, old session, expired candidate, stale token, failed handoff, late callback, and an unmatched independent result must each produce zero unintended sends. Preserve exact message counts at the recorder/server seam.
- **Lifecycle gates:** interrupt, watchdog fail-stop, EOF, reset/resume, permission ask/cancel, and notification with no continuation release every queue/permission wait in bounded time. Include `Stop → continued tool → Stop → result`, `StopFailure` or no Stop, and a rejected notification prompt whose result arrives while a wrapper input waits. A fold must have exactly one T2 result, watchdog end, coordinator settlement, recovery settlement, and token retirement; no synthetic notification terminal is allowed. An independent notification must have its own terminal; missing `result.origin` cannot settle T2 by guess. Existing no-injection default host test must pass through the first meaningful turn. Keep attachment input coverage when correlating ordinary wrapper prompts.
- Run `pnpm build`, `pnpm typecheck`, and full `pnpm test` in affected wrapper packages; run runner typecheck/test because wrapper source affects runtime-asset checks; record all exit codes and unhandled errors. Review the final diff, not just the initial hook implementation. Update `docs/reference/engines/claude-events.md`, `docs/reference/inter-agent/reply-basis.md`, and `docs/reference/inter-agent/errors.md`, with new implementation evidence bound to the final commit.

**Implementation gate:** admission stays disabled until the revised actual SDK/CLI gates demonstrate both a valid same-owner fold with different peer inputs and independent notification admission, plus the retired T1 call's zero-send control. If identity, delivery, or terminal ownership is ambiguous, stop and return evidence for another direction decision. B can land independently while A remains unresolved.
