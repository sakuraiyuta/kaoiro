# Phase 4 — Resident Host Runner

## Goal

Place one resident runner program on each host and make it responsible for the
**lifecycle of the agents on that host** between the server and wrappers. Keep the
direct wrapper topology while introducing a dedicated supervisor for launching,
restarting, and coordinating from the UI ([ADR-0023](../adr/0023-host-runner-architecture.md)).
This is the prerequisite layer for remote spawning from the UI
([#22](https://github.com/sakuraiyuta/kaoiro/issues/22)) and session resumption
([ADR-0014](../adr/0014-session-resume-and-restore.md)).

Issue [#22](https://github.com/sakuraiyuta/kaoiro/issues/22) itself is limited to
the **launch-instruction UI + client→server requests** (spawn/resume) built on this
layer; this phase's tasks (4-1–4-6) cover the host concept, spawn relay, schema,
and runner execution.

## Acceptance Criteria

- [x] The runner stays connected to the server, registers its host, and sends heartbeats.
- [x] On operator instruction, the runner spawns / stops / restarts wrappers on its host.
- [x] The runner supervises one process per wrapper = one agent and isolates crashes.
- [x] Wrappers remain directly connected to the server; the data path does not pass through the runner.
- [x] Duplicate launches are prevented in two stages: server owner fencing + runner-local lock.
- [x] Distribute runner / wrapper as a **self-contained archive** (extract → edit configuration → run with one command, without pnpm install / build on the destination). Single-binary packaging was withdrawn/postponed — revised 2026-07-25 in [ADR-0018](../adr/0018-runner-distribution.md).
- [x] From the launch UI, an operator can specify (host / persona / registered cwd / initial prompt) for a new spawn and resume an existing session from the same UI (medium scope. Arbitrary cwd / arbitrary repo clone are out of the initial version, [#22](https://github.com/sakuraiyuta/kaoiro/issues/22)).

## Implementation Approach (#68 = Tasks 4-4-0–4-5)

# Implementation approach finalized when starting #68 (2026-06-24)

- **Package / type sharing**: Follow “TS package topology” in [ADR-0023](../adr/0023-host-runner-architecture.md) (minimal pnpm workspace + shared `@kaoiro/protocol`, Node side only, dashboard unchanged, wrapper rename deferred).
- **runner config**: JSON configuration file (`host_id` / `server_url` / `personas` / `cwd_allowlist`). Resolve secrets such as tokens from env (`KAOIRO_RUNNER_TOKEN`, etc.), not from the file. Declare available engine types (claude / codex, etc.) in the `capabilities?` field of the `register` payload.
- **Local lock ([ADR-0014](../adr/0014-session-resume-and-restore.md) F4)**: Physically prevent concurrent resume within one runner with an in-memory registry of active `session_id` values. Server owner fencing handles cross-instance cases. Add lockfile hardening across runner restarts later if needed.
- **Stages (backend-first, verify + commit at each stage)**:
  1. 4-4-0: Convert to workspace + extract `@kaoiro/protocol` + migrate wrapper (behavior unchanged).
  2. 4-4a: runner skeleton + server connection + `register` / `heartbeat` (confirm host_registry registration).
  3. 4-4b: `spawn` / `stop` / `restart` supervision loop (wrapper child connection, stop/restart, crash isolation).
  4. 4-5: session JSONL enumeration + `resume` (`--resume`) + T3 cwd existence verification + local lock.

## Launch UI Scope (#22)

- Scope = **medium** (host + persona selection + initial prompt + registered cwd selection).
  Arbitrary cwd / arbitrary repo clone are out of the initial version because they
  expand the RCE surface ([threat-model](../specs/threat-model.md) T1/T5, rejected).
- The **runner config** holds the allowlist of selectable cwd values and declares it
  alongside the persona at registration (move complexity to the host,
  [ADR-0023](../adr/0023-host-runner-architecture.md)). The schema is 4-1 /
  [protocol](../specs/protocol.md) “runner control messages” (finalized in #66).
- **Spawn request = Option A (server completion, [ADR-0024](../adr/0024-agent-instance-identity-and-spawn-auth.md))**:
  the client sends only `{ host_id, persona, cwd, initial_prompt?, resume_session_id? }`.
  The server assigns `agent_id` and completes `server_url` + per-agent token. Secrets
  are not exposed to the client. **persona = type / agent_id = instance**; multiple
  spawns of the same kind use one persona × different agent_ids (D1).
- Spawn authentication is consolidated through runner launch (resident or one-shot).
  Pre-registering per-agent tokens is unnecessary in the spawn path (ADR-0024 D2/D4).
  Token issuance and lifetime are dependent decisions of ADR-0024 (finalized during implementation).
- New / resume switch between “new / resume existing session” through one launch path (provisional).
- Spawn success/failure is reflected in the UI (grid/toast) when `spawn_result` is received (provisional).
- Dashboard lifecycle controls after #22 (implemented): **arbitrary agent name**
  (override persona.name with spawn `name?`), **terminate** (reuse existing `stop`,
  with a warning while running), and **restore** (resume-spawn the same agent_id with
  `restore` control). Seed cwd into SessionPointers at spawn for restoration
  ([protocol](../specs/protocol.md) “client → server launch control”).

## Followups (in-phase but unfinished)

- runner backend (4-4-0–4-5), server completion (4-10), dashboard launch UI
  (4-8/4-9), and **D5** (duplicate live-join rejection) are complete (#22 implemented).
  Residency (4-11, #136) and distribution (4-7, #70) are also complete, so **all tasks
  in this phase are complete**. Only automating asset uploads to the Gitea release was
  separated into #140.
- **D5**: Reject an agent_id with a live owner through the wrapper join path
  (`wrapper_channel`) using **reject-newcomer** ([ADR-0024](../adr/0024-agent-instance-identity-and-spawn-auth.md) D5,
  `AgentStates.connected?/2`). Kicking the existing connection was rejected because it
  would allow token holders to perform hostile eviction. Normal reconnection after an
  abnormal disconnect is delayed only by the socket timeout window (about 60s by default),
  during which the client can retry. The very short join-to-first-envelope window remains
  uncovered (closing it needs a Phoenix.Presence architectural decision, low priority).
  Separated into [#74](https://github.com/sakuraiyuta/kaoiro/issues/74).
- Populate `SessionMeta.summary` (#73, implemented). The runner performs a bounded read
  of the beginning of each session JSONL, preferring `ai-title` and falling back to the
  first user instruction, and returns a minimally exposed (T2 preserved) summary for the
  resume dialog's candidate list.
- Add a time window to the supervisor crash-restart cap (#73, implemented). Reset the
  budget after an incident-free period longer than `RESTART_WINDOW_MS`, so sporadic
  crashes do not exhaust the cap (a tight crash loop remains down).
- Track the low-priority polish gathered above in [#73](https://github.com/sakuraiyuta/kaoiro/issues/73).
  `SessionMeta.summary` / restart-cap time window are implemented; the D5 short window
  was separated into #74.

## Open Questions Blocking This Phase

denylist is [#72](https://github.com/sakuraiyuta/kaoiro/issues/72).
