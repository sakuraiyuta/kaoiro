# Phase 15 — Wrapper UX Parity (Symmetric Claude Code and Codex Usability)

## Goal

Implementation phase for the F4bc addendum to [ADR-0032](../adr/0032-codex-adapter.md),
the F4 addendum to [ADR-0033](../adr/0033-permission-model-dual-axis.md), and F1–F5 of
[ADR-0034](../adr/0034-session-capabilities-advertisement.md). Resolve the asymmetries
identified from momo's (Codex agent) operational perspective through an engine-
neutral envelope schema (`ext.model_source` / `ext.session_capabilities` / resume
difference snapshot) and UI extensions, with the goal of making Codex usable “in the same
style as Claude Code.”

Phase-14 acceptance focused on operating as an engine. This phase resolves the
“asymmetries noticed in daily operation” after it is running.

## Background (Observed Asymmetry)

Asymmetries (D1–D8) exposed by momo (Codex agent) and ao (Claude agent) in
operational verification on 2026-07-11:

- **D1 Model-resolution asymmetry**: `KAOIRO_WRAPPER_DEFAULT_MODEL` affects only the
  Claude CLI and is ignored by the Codex CLI. No model source appears in the
  envelope / UI / log, so the operator cannot distinguish “config specified / env /
  account default / unresolvable.” The shared env sends `claude-opus-4-7` from
  `dev.sh` into Codex spawns, causing 400/404 failures through the ChatGPT-auth path.
- **D2 Permission-UX asymmetry**: The effective value of Claude's single-axis mode
  and Codex's two-axis (sandbox × fixed approval=never) host-fixed constraint are
  not visible in the UI. There is a gap between Claude UX, which assumes an approval
  dialog appears, and Codex UX, which fails outside its range without asking.
- **D3 Config field silently ignored**: Writing `permission_mode`/`allowed_tools`
  for Codex, or `sandbox`/`network_access` for Claude, is silently ignored and can
  cause configuration errors.
- **D4 Attachment asymmetry is invisible**: Codex wholesale-rejects attach_open,
  but the Composer provides no advance hint. Branching by engine name can produce
  false negatives as Codex evolves (such as image input).
- **D5 Axis for question-dialog availability**: Engine names cannot express
  session-level availability differences, such as the possibility that
  `ask_user_question` is unavailable on Free/Go plans.
- **D6 Docs not separated**: `kaoiro.config.example.json` contains only an
  engine=claude-code example. There is no engine × config-field / env mapping table.
- **D7 Effective startup configuration invisible**: The resolved config is not
  visible to the operator, who cannot tell which of config / env / SpawnMessage took
  effect.
- **D8 Configuration differences at resume**: There is no path to detect an
  incident where model / permissions change before versus after resume (restoring
  from a different spawn).

## Acceptance Criteria

- [ ] D1: Both CLIs read engine-specific env vars (`KAOIRO_CLAUDE_CODE_DEFAULT_MODEL` / `KAOIRO_CODEX_DEFAULT_MODEL`) and explicitly implement the resolution priority `launch > env > config > default` internally. The old `KAOIRO_WRAPPER_DEFAULT_MODEL` receives a deprecation warning on the Claude CLI only for one release window; the Codex CLI ignores it (ADR-0032 F4bc addendum)
- [ ] D1: Stamp `ext.model_source: "launch" | "env" | "config" | "default"` in the envelope. Implement both engines. Replace the AgentDetail “account default” label check from an engine-name branch to `model_source === "default"` (remove the Codex special case)
- [ ] D2: AgentDetail's Claude switcher displays the selected effective values (write sandbox / approval) alongside its labels. The Codex side permanently displays an “approval: never (host-fixed, upstream constraint)” badge (ADR-0033 F4 addendum)
- [ ] D2: Add a permission_mode selector to LaunchDialog when engine=claude-code is selected (six values, with a dual-axis tooltip). Relay SpawnMessage.permission_mode from server to wrapper and apply it to the startup mode
- [ ] D2: Display the AgentDetail permission area as two parallel boxes: “work intent (mode)” and “effective write scope (sandbox)”
- [ ] D3: When starting the Codex CLI, if `permission_mode` / `allowed_tools` is specified, output one line to stderr: `config warn: <field> is claude-code-only, ignored on codex`
- [ ] D3: When starting the Claude CLI, if `sandbox` / `network_access` is specified, output one line to stderr: `config warn: <field> is codex-only, ignored on claude-code`
- [ ] D7: On startup, both CLIs output one line to stderr: `[wrapper resolved] engine=<id> model=<name>(source=<launch|env|config|default>) effort=<v>(source=..)? sandbox=<v>(source=..) network_access=<b> approval=<v>(host-fixed?) permission_mode=<v>(ignored?) allowed_tools=<n>(ignored?) persona=<id>` (**include effort only when explicitly specified; omit it when unspecified**). Also expose it in the operator log through the runner tee path
- [ ] D8: Stamp `ext.resume_snapshot` (resolved values before the session starts) and `ext.effective` (values forced this time) in the envelope; if they differ, colocate `ext.resume_drift: {field, prev, now}[]`. Expose it through a stderr warning + AgentDetail badge. Activate only on the resume path; do not emit it for a fresh spawn
- [ ] Stamp `ext.session_capabilities` (both engine implementations, ADR-0034 F1/F4). Fields: `supports_attachments` / `supports_user_input_dialog` / optional `user_input_modes`. **Stamp timing starts at the first state_change immediately after spawn** (do not wait for a session_init-equivalent event. Codex delays `thread.started` until the first turn, so waiting would cause a misleading fail-closed default display. ADR-0034 F1)
- [ ] Enable the Composer attachment button only when `ext.session_capabilities.supports_attachments === true`; otherwise disable it + show the tooltip “Not supported in this session” (ADR-0034 F3). Remove engine-name checks
- [ ] Make AgentDetail question UI inspect `supports_user_input_dialog` (when `user_input_modes` is specified, show conditional unavailability based on comparison with the current mode). Remove engine-name checks
- [ ] Split `wrapper/kaoiro.config.example.json` by engine and add the engine × config field / env mapping table to `wrapper/README.md`. Rewrite the `scripts/dev.sh` env export by engine and document the mapping in comments
- [ ] **Display resolved model / effort / mode in the dashboard immediately after startup** (both Claude / Codex engines): at startup the wrapper **optimistically stamps** resolved values from config / launch into `ext`, and overwrites **only the values** when the SDK report arrives. **Note the source semantics**:
  - **When explicitly specified (launch / env / config)**: Stamp `model` + `model_source=launch|env|config` immediately after startup. **Keep source as launch/env/config even after SDK confirmation** (the field communicates the value's origin, so rewriting it to `default` after SDK confirmation would falsely claim “the account default was used”). Only the value may be updated by the SDK report (for example, Claude may expand an alias to its canonical name).
  - **When unspecified**: Do not stamp either `model` / `model_source` immediately after startup. `model` + `model_source="default"` first appear when the SDK report arrives.
  - **Exception: do not stamp effort when no explicit startup specification (config.effort / launch.effort) exists**, because the wrapper does not know the SDK default (show it immediately only when explicitly specified; waiting for the SDK report when unspecified is the accurate behavior). `effort_source` follows the same semantics.
- [ ] All wrapper packages (core / agent-common / claude-code / codex) pass their tests. All dashboard / server / runner regression tests pass. The protocol envelope type additions are verified end to end through both engines and the dashboard
