## Engine selection and acquisition

`engine_executable` is an optional launch-file field. At each wrapper spawn
and Claude catalog probe, the runner selects the executable for its own
release's pin when that executable exists in the shared store. Otherwise
it uses the engine inside the release tree. Ordinary launches need no
configuration migration. Antigravity and Grok continue to use host CLIs.

The `engines install` subcommand and
`deploy/kaoiro-runner-engines.sh` acquire enabled Claude and Codex engines.
New update and bootstrap tools call the candidate's acquisition script.
Update acquires before stopping the runner; bootstrap acquires before
switching. Missing configuration skips acquisition; unreadable or invalid
configuration fails. A missing acquisition script is refused by these tools.
See the [update runbook](../operations/runner-update-and-rollback.md#engine-acquisition).

Downloads are checked against lockfile-derived integrity. A newly acquired
Codex binary is also checked against the release's native-identity record.
Existing stored pins are reused without rehashing or downloading. Acquisition
has no timeout and can wait before activation if the registry stalls. The
store is not automatically pruned; see the
[engine store](../reference/configuration/runner.md#engine-store) and
[update runbook](../operations/runner-update-and-rollback.md#engine-acquisition).

## Codex models and state

GPT-6.2-Sol and GPT-6.2-Astra appear in the static catalog with `low`,
`medium`, `high`, `xhigh`, `max` and `ultra` efforts; the default is `low`.
The measured client floor is 0.170.0, rather than a claim about the first
upstream release supporting each model. Existing model rows remain.
See the [catalog](../reference/engines/codex-model-catalog.md).

The new native pin migrates Codex state. Before stopping the runner, install
and verify the candidate without activation and run its private classification
preflight on the configured Codex home. A refusal aborts the update; unknown
entries need a separately reviewed classification, not deletion or renaming.
The candidate updater stops the runner and snapshots state before activation.
Keep the snapshot and its operation record outside cloud synchronization and
external backups until the operator decides retention is no longer needed.

Rollback uses the same verified physical updater and the retained snapshot.
It restores state and starts the recorded previous release. Conversations
created after the snapshot are lost; peers using 6.2 may need the operator to
choose an older model when restarting. Current credential entries are moved
into the restored home, not rolled back from the snapshot. State restoration
and restoring offline peers are separate operations.

When a completed agent-message item carries moderation metadata, the wrapper
writes one diagnostic line to stderr with a fixed classification: `show`,
`hide`, `block`, `restricted_unspecified` or `unknown`. The diagnostic contains
no message body, reason, annotation or item ID. A failed diagnostic write does
not change the turn's result. The existing stderr path carries these lines to
the runner log under the standard service unit.

Known limitation: kaoiro preserves its existing text display and history even
when upstream attaches `hide` or `block` instructions. The body still appears
in the screen, ordinary logs and restored history. If a moderation diagnostic
is recorded even once, ask the operator to reconsider this handling. See the
[Codex adapter contract](../../wrapper/codex/README.md#moderation-display-instructions).

  ([issue #1190](https://github.com/sakuraiyuta/kaoiro/issues/1190)).

## Claude hook progress and credential protection

While a hook runs, Claude Code now reports progress every 30 seconds.
kaoiro's turn watchdog counts each frame as activity and restarts its full
inactivity interval. Recovery after a hook can therefore happen later than
before, including with the default hook timeout. Hooks in a row add up;
one hook's timeout does not bound the delay for a whole turn. A hook whose
timeout exceeds the inactivity limit keeps the watchdog from firing while
it runs. The watchdog remains active and fires after a full interval with
no further frames. Long tools already received this treatment.

A `Write` to the Claude CLI's credentials file is now refused even in
`bypassPermissions`. Both changes are accepted vendor behavior; this
release does not filter hook heartbeats out of watchdog progress. See the
[SDK evidence](../evidence/claude/issue-1185/sdk-0.3.327-2026-11-18.md).

## Operator steps and rollback

Update the runner and bundled wrappers. The server and dashboard remain on
v2026.11.16.1: neither has a code change in this release range. The launch
dialog's host/server revision mismatch remains. Check identities and dirty
flags directly, follow the FS + TL start gate, and retain a recovery shell
that does not depend on any agent.

Use the installed candidate's fixed physical updater for the pin-changing
update, with explicit installation root, service, tarball, Codex home and a
new snapshot path. Do not invoke it through `current` or `previous`. The
updater performs acquisition; do not add manual acquisition. Check expected
store entries, identities, connections, completed turns and each peer's
restoration result. Follow the
[state backup procedure](../operations/runner-update-and-rollback.md#codex-state-backup).

Rollback returns to retained v2026.11.19.1 by passing the retained snapshot
to that same physical updater with `--restore-codex-backup` and the same
Codex home. It performs restoration, switching and startup without engine
acquisition. A plain `switch --rollback` cannot cross the native hashes.
If restoration fails, preserve state and use the runbook's recovery path.
[Fresh setup](../operations/codex-home.md#fresh-setup-after-failed-snapshot-recovery)
is a separate operator choice that accepts loss of history, login and caches.
The server stays unchanged.

  [code landing record](https://github.com/sakuraiyuta/kaoiro/issues/1211#issuecomment-7013319820).
- Signed-in product-entry checks on that code completed with both 6.2 models,
  model and effort switches in both directions, a cold resume and a 6.1
  control. These observations do not establish entitlement for other accounts
  or verification of the final tagged artifacts.
- Final-artifact release checks remain separate from code approval. At note
  preparation, the final tagged candidate's real systemd update, snapshot
  restoration and old-native resume have not been measured. The production
  Codex home's private classification preflight is also still required.
  Follow the [FS + TL release gate](../operations/high-risk-change-release.md)
  and [state backup procedure](../operations/runner-update-and-rollback.md#codex-state-backup).
- State-aware migration requires Linux/systemd with unified cgroup v2.
  Acquisition and engine-launch checks must cover the platform used for the
  release; no result here claims coverage of every supported platform.
- A stored Codex executable can differ from the file in the release tree
  that the switch guard hashes. Acquisition checks the downloaded artifact;
  the guard does not detect later modification of an already stored binary.
- A release missing both the entry and its manifest line can pass install
  and switch; its launch shim stops with exit 78. Removing only the entry
  is rejected by the verifier.
- Preparatory state checks use credential-free homes. Backup and restoration
  of a real signed-in production home are not measured in advance. External
  writers are not scanned by the updater and must remain stopped during the
  maintenance interval.
- The release card must state whether detached state-aware update was measured
  and give the final artifact's actual coverage. This note does not claim a
  successful detached update on the final candidate.
- A real response carrying moderation metadata, and the resulting new
  diagnostic line in the journal, have not been observed. Tests fix the
  diagnostic's contents and failure isolation; the existing journal path was
  observed separately. See the
  [adoption evidence](../evidence/codex-app-server/pin-0.170.0-adoption-gates-2026-11-19.md).
