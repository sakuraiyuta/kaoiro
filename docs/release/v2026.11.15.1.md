# Release v2026.11.15.1

- Previous production release: [v2026.11.14.2](v2026.11.14.2.md)
- Range: `v2026.11.14.2..v2026.11.15.1`
- Release class: TL for every engine, not FS
  ([High-risk change release](../operations/high-risk-change-release.md)).
  The TL path list catches `wrapper/agent-common/src/inter_agent.ts`, the
  `cli.ts` of all four engines, and the Grok `host.ts` and `acp/session.ts`.
  Grok changes how a turn is sent, attributed, interrupted and ended. For
  the other three engines the only change is that a pending reply wait no
  longer holds a stopping wrapper, but the shared module is on every
  engine's turn path, so no engine is a standby for another. No
  FS-listed file, tagging mechanism, engine SDK, CLI or native pin changes.
  The server, dashboard and runner have no source change in this range.

## Highlights

- **Grok peers take part in work items.** Grok negotiates `work_control` and
  registers the shared work tools
  ([issue #1123](https://github.com/sakuraiyuta/kaoiro/issues/1123)).
- **Grok supports session reset.** The operator's reset, the agent's
  `request_session_reset` and a director's `request_peer_session_reset` with
  a Grok target work in modes `new` and `clear`
  ([issue #658](https://github.com/sakuraiyuta/kaoiro/issues/658)).
- **Turns Grok starts on its own stay out of the operator's turn.** They are
  shown as logs, and their permission requests are refused
  ([issue #1128](https://github.com/sakuraiyuta/kaoiro/issues/1128)).
- **An interrupt stops the interrupted Grok turn's background tasks**
  ([issue #594](https://github.com/sakuraiyuta/kaoiro/issues/594)).
- **A stopping wrapper no longer waits on a pending reply timer**, on every
  engine ([issue #1130](https://github.com/sakuraiyuta/kaoiro/issues/1130)).

## Changes

### Grok

- Work items: the adapter negotiates `work_control` v1 and registers
  `work_status`, `work_op_result` and `delivery_status`. A work notice reaches
  the model as an input turn. Work operations follow the server's existing
  authority rules. Grok can request early and yield delivery as a sender; its
  declared receiving modes stay `early: "none"` and `yield: "none"`. It does
  not register `request_peer_session_reset`, so a Grok agent cannot request a
  peer's reset ([Grok engine reference](../reference/engines/grok-acp.md)).
- Session reset: the adapter advertises `supports_session_reset: true` with
  `session_reset_modes: ["new", "clear"]`. A reset is the runner's existing
  fresh relaunch; both modes relaunch the same way and differ only on the
  server. `request_session_reset` asks the operator on every call, with no
  autonomous skip. The wait is bounded at 300 s, or at
  `permission_timeout_ms` when that is shorter, and a timeout denies. An
  approved reservation is sent only when the reserving turn's prompt returns
  with a stop reason other than `cancelled`; otherwise it is dropped and the
  agent is told
  ([Session reset](../reference/engines/grok-acp.md#session-reset),
  [session tools](../reference/inter-agent/session-tools.md)).
- The host's drain loop re-checks its queue before it stops, so a turn
  queued while the loop awaited its idle switch step with an empty queue is
  no longer left waiting for the next input.
- Prompt ownership: every `session/prompt` carries
  `_meta.promptId: "kaoiro-<uuid>"`, and only that prompt is the operator's
  turn. A prompt Grok starts on its own (`task-completed-*`,
  `notifications-*`, `interject-fallback-*` or any other id) appears as a
  `system` line `Grok started a turn on its own (<reason>)`, its assistant
  text and tool calls, and `Grok's own turn ended`. It never enters a kaoiro
  turn's result, events or state. A permission request reaches the operator
  only when a `tool_call` of the operator's prompt recorded its call; any
  other request is answered `cancelled` and logged. A context reading counts
  only for the prompt it was taken under
  ([Turns Grok starts on its own](
  ../reference/engines/grok-acp.md#turns-grok-starts-on-its-own)).
- Interrupt: while the operator's prompt waits behind a self-started turn, an
  interrupt cancels that turn and cancels the operator's prompt once it
  runs. With no operator turn active, an interrupt cancels a running
  self-started turn.
- Background tasks: when the operator interrupts a turn and its prompt
  returns `cancelled`, the wrapper sends `_x.ai/task/kill` for each task that
  turn moved to the background. A cancel the operator did not ask for, a
  normal end and a session reset kill nothing. A failed, unexpected or
  missing answer (2 s) writes one stderr line and the system log line
  `Could not stop a background task of the interrupted turn (<reason>)`; the
  turn's result does not change
  ([Cancellation and background tasks](
  ../reference/engines/grok-acp.md#cancellation-and-background-tasks)).
- Recorded limits, with no behavior change: receiving early input stays
  unsupported
  ([issue #1124](https://github.com/sakuraiyuta/kaoiro/issues/1124)),
  reply-basis v1 stays not negotiated because Grok MCP calls carry no proven
  turn-origin identity
  ([issue #1126](https://github.com/sakuraiyuta/kaoiro/issues/1126)), and
  attachments stay unsupported, with notes on how Grok treats each ACP
  prompt content block
  ([issue #1127](https://github.com/sakuraiyuta/kaoiro/issues/1127)).

### All wrappers

- When a wrapper stops, every `wait_for_response` wait pending at that moment
  is released the same way as a timeout (`reply_pending=true`). This neither
  cancels the send nor ends the conversation. The wait's timer, of up to
  300 s, no longer keeps a stopping process alive. Claude Code, Codex,
  Antigravity and Grok all call the release from their shutdown path
  ([send and wait](../reference/inter-agent/send-and-wait.md)).

## Operator steps

- Advance the server and the runner to the same release, updating the server
  while the runner is stopped. The server has no code change in this range.
  This release requires no new server store, data migration, environment
  variable, Compose setting, runner capability or persona-pack update.
- Treat the release as TL for every engine. Run the start gate (recommended
  for TL), then follow
  [Release and restore the fleet](
  ../operations/high-risk-change-release.md#4-release-and-restore-the-fleet).
  No agent of another engine is a standby; plan on the plain shell. After
  restoration, check a turn on each engine in use.
- A session reset of a Grok agent is now accepted. In the dashboard
  composer, `/new`, `/clear` or `/reset` sent to a Grok agent now resets its
  session. Before this release the composer sent that text on as an ordinary
  instruction, and a reset request was refused with
  `unsupported_session_reset`.
- A Grok configuration whose hooks ask before MCP calls adds Grok's own
  permission requests before the wrapper's reset dialog.

## Rollback

- Return the server and runner to v2026.11.14.2 with the usual procedures.
  No store format needs conversion.
- Under the older wrapper, a Grok agent again refuses session reset, does
  not negotiate `work_control`, mixes a self-started turn into the
  operator's turn and leaves background tasks alive after an interrupt.
  The older Grok wrapper has no work tools, so it cannot act on a work item
  assigned to it.
- Under the older wrapper, a stop during a pending `wait_for_response` can
  again keep the wrapper alive until the wait's timer fires.

## Known limits

- The Grok behavior was measured on Grok Build 1.0.52 and one host
  configuration. The native Grok checks are not part of CI.
- The reset approval bound limits the wrapper's wait but does not guarantee
  an answer before Grok gives up: Grok waited for a blocked kaoiro MCP call
  for the full 600 s in one measured run, and its own timeout is unmeasured.
- A self-started Grok turn can still run a tool that needs no permission.
  After a kill, Grok starts one `task-completed-*` turn per killed task and
  the next input waits behind them. Tasks moved to the background after the
  interrupted prompt returned are not killed.
- Grok's auto mode can refuse, before it runs, a tool call that only a
  peer's message asked for, such as an assignment acceptance. The refused
  acceptance leaves the work `nominated`.
- Releasing reply waits at stop is not a terminal state: a wait that starts
  after the release is not refused and is not released either, although its
  timer cannot keep the process alive.
