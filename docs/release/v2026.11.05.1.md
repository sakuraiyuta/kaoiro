# Release v2026.11.05.1

- Previous production release: [v2026.11.04.1](v2026.11.04.1.md) (`d97bb59c`, server) and [v2026.11.01.1](v2026.11.01.1.md) (`c615ea60`, runner)
- Range: `v2026.11.04.1..v2026.11.05.1`
- Release class: FS and TL
  ([High-risk change release](../operations/high-risk-change-release.md)).
  `runner/deploy/**`, `wrapper/core/src/transport.ts` and
  `wrapper/agent-common/src/inter_agent.ts` changed.

## Highlights

- **Work items have five operations.** `assign`, `accept_assignment`,
  `decline`, `complete` and `cancel` remain. Review and transfer operations
  are rejected, and `work_check` and `work_transfer_ack` are removed
  ([issue #965](https://github.com/sakuraiyuta/kaoiro/issues/965)).
- **Normal messages can continue a work.** A normal or early message may carry
  `work_id` and link a new conversation to an active work. The guarantee stops
  at the caller's `new_conversation` declaration.
- **The release canary is gone.** After a high-risk update the operator restores
  the fleet in bulk and records each tile. A turn-lifecycle defect can reach
  every restored peer before it is seen
  ([issue #709](https://github.com/sakuraiyuta/kaoiro/issues/709)).
- **The Codex recovery table is gone.** `recover`, `resume`, snapshots and
  state-aware updates stay. A refusal prints its message and one safety line,
  and the record's `next` lines when a record is found.

## Changes

### Server

- Removed operations return `unsupported_work_operation` before identity and
  authority checks, after the receipt lookup.
- `complete` and `cancel` no longer check `expected_revision`, `subject_hash`
  or verdicts.
- Reset and yield authorization, `operation_id` idempotency and capacity limits
  are unchanged.
- Stored work records keep their shape. Old values stay on the wire but no
  server decision reads them. Physical removal is a separate design.

### Protocol and wrapper

- `WorkControlOp` has five operations. `WorkReceiptOp` keeps fifteen so older
  receipts and delivered messages stay readable.
- A failed link returns the reason and retry guidance on the tool result.

### Runner deploy

- Class-specific refusal advice and the generated recovery table are removed.
- The shell lock refusal prints the safety line. Other shell refusals, such as
  the install script's, do not.

## Operator steps

- This release must deploy server and runner together. **Stop every runner
  before the server commit** and follow
  [Coordinated server and wrapper updates](../operations/runner-update-and-rollback.md#coordinated-server-and-wrapper-updates).
- Roll back as a pair, runner stopped first. A server-only rollback can
  silently leave a `work_id` message unlinked and make a later yield fail.
- No new environment variable, no new server store and no stored format change.
  The deploy CLI does not ask to accept a new store.
- Before production, measure `prepared` and `start-intent` recovery on this tag.
  A failure blocks the release
  ([issue #709](https://github.com/sakuraiyuta/kaoiro/issues/709)).

## Known limits

- Grok wrappers show `work_control` but cannot accept an assignment. This
  predates the release.
- Scope of the safety line is listed above.
