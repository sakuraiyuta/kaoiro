# Release v2026.11.16.1

- Previous production release: [v2026.11.15.1](v2026.11.15.1.md)
- Range: `v2026.11.15.1..v2026.11.16.1`
- Release class: FS and TL
  ([High-risk change release](../operations/high-risk-change-release.md)).
  The FS path list catches `runner/src/transport.ts`: the runner's server
  connection changes how it reconnects, and the runner is on every engine's
  start path, so no engine is a standby for another. The TL path list
  catches the `host.ts` and `cli.ts` of Claude Code and of Grok, and the
  Grok `acp/session.ts`. Claude Code changes its tool-call hooks, the yield
  cut and the resume-note budget; Grok changes how an instruction is staged,
  sent and dropped. The Codex and Antigravity wrappers, `wrapper/core` and
  `wrapper/agent-common` have no source change. No runner deploy script,
  tagging mechanism, engine SDK, CLI or native pin changes; the Grok wrapper
  gains `officeparser` and `fflate` at the versions the Claude Code wrapper
  already uses. The protocol version stays 0.

## Highlights

- **The dashboard formats Markdown bodies in a Web Worker.** A body shows
  its complete source as plain text until its formatting arrives, and one
  heavy body can no longer block the page
  ([issue #617](https://github.com/sakuraiyuta/kaoiro/issues/617)).
- **Tail follow in the agent log is judged by scroll position**, so late
  formatting keeps the place the operator was reading
  ([issue #617](https://github.com/sakuraiyuta/kaoiro/issues/617)).
- **Grok peers accept attachments**: images, text and code, Office files
  and PDFs
  ([issue #1143](https://github.com/sakuraiyuta/kaoiro/issues/1143)).
- **A Claude Code peer no longer fail-stops when the CLI reads its resume
  note more than two seconds after a compaction**
  ([issue #1158](https://github.com/sakuraiyuta/kaoiro/issues/1158)).
- **A director's yield waits for a running MCP call of a Claude Code
  peer**, so the call's result reaches the model
  ([issue #521](https://github.com/sakuraiyuta/kaoiro/issues/521)).
- **A Grok peer explains a permission stop after a failed observation**
  ([issue #1157](https://github.com/sakuraiyuta/kaoiro/issues/1157)).
- **The runner reconnects after a channel error followed by socket close
  1000** ([issue #914](https://github.com/sakuraiyuta/kaoiro/issues/914)).
- **Operator dashboards receive a fresh host list after a persona
  rebuild** ([issue #970](https://github.com/sakuraiyuta/kaoiro/issues/970)).

## Changes

### Dashboard

- Markdown formatting
  ([issue #617](https://github.com/sakuraiyuta/kaoiro/issues/617)): the
  bodies of the agent log and the expanded entries of the status-line
  change log are lexed in one Web Worker per dashboard page. Until its
  result arrives, a body shows its complete source as plain text under the
  note "Formatting; the complete source is shown while waiting". Card and
  panel heads and collapsed history summaries stay synchronous
  ([Asynchronous Markdown bodies](
  ../reference/ui/design.md#asynchronous-markdown-bodies)).
- Each body has 1,000 ms from the moment the worker starts on it. A
  timeout, excessive nesting or a failure while running that body leaves
  the body as plain text under the existing "Shown as plain text" note,
  without a retry, and the next body gets a fresh worker. A failure before
  the worker starts a body disables formatting until the page is reloaded;
  bodies then show "Formatting is unavailable. Reload the page to try
  again". No source text is cut or lost in any of these cases.
- Bodies are formatted first come, first served, one at a time. Results
  that settle while a later body is being lexed are applied together 50 ms
  after the first of them. Parsing, sanitizing, Mermaid and layout stay on
  the main thread under the same sanitizer policy.
- Scrolling: late formatting keeps what the log was holding — the bottom
  pin, a remembered position, the show-earlier anchor, the body of a
  timeline jump or a centered tool partner. A scroll that leaves the log
  more than 0.5 px from where that correction put it is the operator's and
  is kept. The bottom pin resumes only when the operator reaches the end.
  A timeline or tool jump ends on `scrollend`, or after 150 ms without
  scrolling in a browser that lacks the event. A jump that lands at the end
  of the log follows later output.
- Two differences from the previous release remain by design: a click that
  moves nothing no longer stops a timeline jump, and a script or browser
  extension that scrolls inside `requestAnimationFrame` while bodies are
  still being formatted is returned to the tail.

### Claude Code

- Resume note after compaction
  ([issue #1158](https://github.com/sakuraiyuta/kaoiro/issues/1158)): the
  note's idle budget is `max(pending_receipt_root_timeout_ms, 30 s)`, so
  30 seconds by default. Before this release it was the two-second
  live-push budget, and a correctly delivered note that the CLI read later
  was rejected as `missing_hook`, which stopped admission until the wrapper
  was relaunched. Live pushes keep the plain setting. `resume_pending`
  records the value as `idle_limit_ms`. A resume note that never arrives
  still fail-stops, and the 30-minute total budget is unchanged
  ([Reserved resume notes after compaction](
  ../reference/engines/claude-events.md#reserved-resume-notes-after-compaction),
  [measurements](../evidence/claude/2026-11-16-compact-resume-latency.md)).
- Director yield
  ([issue #521](https://github.com/sakuraiyuta/kaoiro/issues/521)): a
  granted cut waits until the SDK tool result of a running root MCP call is
  received, so a call such as `send_to_agent` is no longer cut off before
  its result reaches the model. A call still waiting in a permission dialog
  is aborted as before. While the cut waits it reserves the push slot: new
  peer early inputs stay queued, and operator early input that cannot fold
  becomes an operator root. The wait does not consume the pending-receipt
  deadline and adds no total limit of its own
  ([Claude recipient handoff](
  ../reference/inter-agent/delivery.md#claude-recipient-handoff),
  [measurements](../evidence/claude/issue-521-mcp-yield-2026-11-15.md)).

### Grok

- Attachments
  ([issue #1143](https://github.com/sakuraiyuta/kaoiro/issues/1143)): the
  adapter advertises `supports_attachments: true` with no
  `attachment_types`, so the dashboard offers the attachment controls for
  a Grok agent. Images go as ACP `image` blocks, text and code and the
  extracted text of `.docx`, `.xlsx` and `.pptx` as `resource` blocks, and
  a PDF as a `resource_link` to a file the wrapper writes when the turn
  starts and removes when it ends
  ([Prompt content blocks and attachments](
  ../reference/engines/grok-acp.md#prompt-content-blocks-and-attachments),
  [ADR-0025](../adr/0025-file-upload-wire-and-wrapper-rendering.md)).
- An instruction whose blocks serialize to more than 33,488,896 bytes is
  refused with `instruction_rejected` `total_request_over`, and Grok keeps
  running. An instruction naming an upload that has not been closed is
  refused with `timeout`, and the upload stays usable. An interrupt drops
  pending uploads and every instruction with attachments whose turn has not
  started; a queued text-only turn still runs.
- Grok drops an image with a side under 8 pixels or fewer than 512 pixels;
  the adapter shows each such notice as a system line `Grok: <note>`.
- Permission observation
  ([issue #1157](https://github.com/sakuraiyuta/kaoiro/issues/1157)): when
  Grok cannot confirm a permission outcome, for example after a model
  error, the adapter now reports `permission_failed` also at the launch
  revision and writes one system line saying that later turns are held
  until the operator selects permission again, and that an instruction
  rejected with `permission_gate_blocked` must be resent. The stop itself
  is unchanged
  ([Permission switching](
  ../reference/engines/grok-acp.md#permission-switching)).

### Runner

- Transport recovery
  ([issue #914](https://github.com/sakuraiyuta/kaoiro/issues/914)): a wire
  `phx_error` on the runner's own topic followed by socket close 1000 now
  replaces the socket after 1, then 2, then 5 seconds. Before, the runner
  stayed disconnected until it was restarted, for example when it resumed
  from a pause after a server VM restart. A successful join, a socket open
  or a wire `phx_close` cancels the pending recovery; a plain close 1000,
  an intentional close and a configuration replacement do not reconnect
  ([Runner control and launch](../reference/protocol/runner-control.md)).

### Server

- Persona rebuild
  ([issue #970](https://github.com/sakuraiyuta/kaoiro/issues/970)): after
  the server rebuilds its personas, each connected operator dashboard
  receives a `hosts` push resolved at that moment, so a pack added to a
  running server reaches the launch dialog without a restart. A failed
  notification is logged and does not fail the rebuild
  ([Persona asset distribution](
  ../reference/protocol/persona-delivery.md#persona-asset-distribution)).

## Operator steps

- Advance the server and the runner to the same release, updating the
  server while the runner is stopped. The server image carries the server
  and dashboard changes above. This release requires no new server store,
  data migration, environment variable, Compose setting, runner capability
  or persona-pack update.
- Treat the release as FS and TL. Run the start gate (required for FS),
  then follow
  [Release and restore the fleet](
  ../operations/high-risk-change-release.md#4-release-and-restore-the-fleet).
  No agent is a standby; plan on the plain shell. After restoration, check
  a turn on each engine in use.
- Reload open dashboard pages after the server update to load the worker.
  No browser-storage migration or clearing is required.
- `claude_code.pending_receipt_root_timeout_ms` can lengthen the resume
  note's idle budget but can no longer shorten it below 30 seconds.
- After the release, check the Claude Code receipt lines in the runner
  journal: `resume_pending` carries `idle_limit_ms`, and no
  `resume_receipt_rejected` with `missing_hook` follows a compaction
  ([issue #1158](https://github.com/sakuraiyuta/kaoiro/issues/1158)).
- A Grok turn with PDFs writes them under the OS temporary directory of
  the runner host, in `kaoiro-grok-attach-<SHA-256 of agent_id>-XXXXXX`
  (`0700`, files `0600`), for the length of the turn.

## Rollback

- Return the server and runner to v2026.11.15.1 with the usual procedures.
  No store format needs conversion. Reload dashboards to load the restored
  release.
- Under the older Claude Code wrapper, a resume note read later than two
  seconds after a compaction can again fail-stop the peer, and a director's
  yield can again cut off a running MCP call.
- Under the older Grok wrapper, attachments are refused again and the
  permission stop after a failed observation is silent again. The older
  wrapper does not sweep a PDF directory that a crashed newer wrapper left
  behind.
- Under the older runner, a channel error followed by close 1000 again
  leaves the runner disconnected until it is restarted.
- Under the older server, a persona pack added to a running server again
  needs a server restart to reach the launch dialog.

## Known limits

- The dashboard changes were measured in Chromium 151. Touch input and
  fling on real devices, Safari releases without `scrollend` on real
  hardware and other browsers were not measured. The browser gate is a
  manual check outside CI.
- Formatting order has no maximum wait for a long expanded history, and
  parsing, sanitizing, Mermaid and layout on the main thread have no time
  bound.
- The Grok attachment behavior was measured on Grok Build 1.0.52; `.xlsx`,
  `.pptx`, WebP and GIF delivery was not measured against the live model.
  Grok keeps its own copy of each sent image in its session directory, and
  large images shorten the dashboard history replayed on resume.
- The Grok permission notice does not lift the stop; automatic recovery is
  [issue #1159](https://github.com/sakuraiyuta/kaoiro/issues/1159). The
  launch-revision report was not observed on a running server's audit
  timeline.
- The CLI step behind the late resume note is not identified. A note that
  arrives after the 30-second idle budget still fail-stops the peer.
- While a yield cut waits for an MCP call, switching the delivery policy
  off does not wake it; the reservation stays until the call ends. MCP
  calls inside subagents or SDK notification roots are not covered.
- The runner's transport recovery does not clear an old server VM's
  Registry refusal; the
  [manual recovery procedure](
  ../operations/codex-backend-switch.md#read-only-supervisor-observation)
  still applies. A real production VM restart was not exercised.
- [Issue #970](https://github.com/sakuraiyuta/kaoiro/issues/970) retains
  `needs-verify`: the production report was not tied to this defect, so
  check on the deployed server that an added persona pack reaches the
  launch dialog without a restart.
