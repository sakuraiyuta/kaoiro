# Release v2026.11.23.1

- Previous release: [v2026.11.21.1](v2026.11.21.1.md), for the server, the
  dashboard, the runner and the wrappers.
- This release updates the server, the dashboard, the runner and the
  wrappers to one tag.
- Release class: FS + TL, all engines.
  [High-risk change release](../operations/high-risk-change-release.md)

The three units belong to the Antigravity migration to ACP
([issue #1181](https://github.com/sakuraiyuta/kaoiro/issues/1181)).

## Antigravity authentication

- The runner starts an Antigravity agent, and asks `agy` for its model list,
  only when `antigravity.auth` in the runner configuration declares
  `google-cloud-adc` or `google-cloud-sign-in` and the markers of that method
  are present in the runner's environment. Personal sign-in and AI Studio
  keys are not supported methods.
  [ADR-0077](../adr/0077-antigravity-authentication.md)
  [Issue #1236](https://github.com/sakuraiyuta/kaoiro/issues/1236)
- Without a usable declaration, a launch, a restore and a session reset of
  an Antigravity agent are refused with `engine_auth_unsupported`, and the
  launch dialog offers the built-in model list instead of the one `agy`
  reports. A value other than the two methods is refused with
  `engine_auth_invalid`. The runner journal names the missing marker. The
  runner itself and the other engines start as before.
- The server accepts the two reasons in a session reset result, and the
  dashboard explains them in its launch, restore and reset messages.
- The runner checks the declaration, the environment markers and that the
  ADC source is a readable regular file. It never opens the credentials and
  cannot tell which account or project they belong to.

## Antigravity over ACP

Antigravity agents no longer use `agy --print` with stream-json and the CLI
bridge. [ADR-0078](../adr/0078-antigravity-over-acp.md)
[Issue #1238](https://github.com/sakuraiyuta/kaoiro/issues/1238)

- **One `agy` process per input.** Every input starts its own `agy acp`
  process, which is retired when the input settles; the conversation
  continues through `session/resume`. Every turn pays a start (a median of
  2.2 s to 2.7 s with `agy` 1.5.14). No process stays between turns, and a
  background command ends with its process at the latest.
- **Waiting for background work.** A prompt stays open while its own
  background work runs, up to 10 continuations. Waiting costs model tokens.
  A start is refused while `agy`'s hook list shows another enabled Stop hook.
- **The kaoiro gate is the only permission check.** `agy`'s own prompts are
  off. A permission change takes effect with the next input. The cells are in
  [Antigravity tools and permissions](../reference/engines/antigravity-tools-permissions.md#evaluation-order).
  What an operator notices:
  - In `read-only`, tools the gate does not know are denied instead of asked.
  - In `workspace-write`, shell commands are denied while network access is
    off and asked one by one while it is on (`never` denies them).
  - A command's `Cwd` no longer decides anything.
  - A gate fault is final: the agent accepts no input until it is restarted
    or its session is reset. The automatic recovery is removed.
  - A tool request outside a turn is denied with a reason.
- **Questions.** `agy` cuts a kaoiro tool call after 180 s. A question's
  dialog closes at that cut, and at the latest when its turn ends.
- **No rate limit gauge.** Antigravity agents report no `rate_limits`; the
  `/usage` probe is removed.
- **A 429 is an API error.** How `agy` reports a rate limit over ACP is not
  measured, so a JSON-RPC error reaches the operator as the error detail and
  a waiting peer as `api_error`, not `rate_limit`, also when its message
  mentions 429 or `RESOURCE_EXHAUSTED`.
- **Model list.** The built-in list used when `agy models` fails drops three
  values that `agy` 1.5.14 rejects: `gemini-3.1-pro-high`,
  `gemini-3.1-pro-low` and `gpt-oss-120b-medium`.
- **Configuration.** `antigravity.epoch_idle_ms` and
  `KAOIRO_ANTIGRAVITY_EPOCH_IDLE_MS` are still checked but have no effect.
- **Known limitations.** Under `danger-full-access`, and for an approved
  command that bypasses the sandbox, a command can outlive `agy`. Under the
  launch flags in use, the sandbox was measured not to confine writes in the
  home directory or outbound HTTPS, so the gate's cells are the enforcement.
  The full list is in
  [Known limitations](../reference/engines/antigravity-tools-permissions.md#known-limitations).

The behaviour was measured with `agy` 1.5.14 under service-account ADC in an
isolated home
([native acceptance](../evidence/antigravity/agy-1.5.14-acp-native-acceptance-2026-11-23.md)).
Resuming a conversation created by an earlier release is not measured.

## Shared ACP client and HTTP tool host

The resident ACP client and the authenticated HTTP tool host moved from the
Grok wrapper to `@kaoiro/agent-common`, where Antigravity uses them too. Grok
agents keep their behaviour. The Grok wrapper's direct `zod` range moved to
version 4, so the workspace resolves one `zod` and one ACP SDK (1.8.0).
[Issue #1237](https://github.com/sakuraiyuta/kaoiro/issues/1237)

## Upgrade and recovery

1. Before the update, on every runner host that enables `antigravity`, set
   `antigravity.auth` in the runner configuration and the markers of the
   chosen method in the runner's service environment, as described in
   [Antigravity authentication](../operations/runner-install.md#antigravity-authentication).
   The runner of the previous release does not read the key or check the
   variables, so they can stay in place across a rollback. A host that skips
   this step keeps its other engines and refuses Antigravity launches.
2. Prepare the server and runner rollback targets and verify the runner
   archive against the digest recorded for this release.
3. Deploy the server and its dashboard first, so the new reset failure
   reasons are understood. Confirm health and the existing runner's
   connection, then update the runner and the wrappers.
4. Check the runner's actual version, registration and connection before
   restoring agents. Restore the selected agents and check their sessions
   and wrapper versions.
5. Start one Antigravity agent and check its first turn. A failure there
   concerns that engine only: stop the agent and keep the other engines
   running.

The Codex and Claude Code pins are unchanged, so a runner rollback to the
previous release is a same-native switch.
